# AgoraNote

AgoraNote turns study input — text documents or lecture recordings — into active, searchable study
material: ordered chapters, each with a summary, key concepts, Q&A flashcards, study aids and a
scored multiple-choice quiz. Correct answers earn points, and enough points in a chapter unlock
the next chapter's quiz.

**Stack:** Vite + React (plain JS) · FastAPI (Python 3.12) · PostgreSQL · Redis + Celery ·
Docker Compose for local development · Railway for deployment.

## Run it locally

Requirements: [Docker Desktop](https://www.docker.com/products/docker-desktop/) (includes Docker Compose).

```bash
cp .env.example .env
docker compose up
```

Then open:

- Frontend: http://localhost:5173
- API health check: http://localhost:8000/api/health
- API docs (generated by FastAPI): http://localhost:8000/docs

The first start takes a few minutes (building the backend image, `npm install`).
No API keys are needed: in development the AI steps run in mock mode.

### Useful commands

```bash
# Check the Celery worker runs tasks (prints "pong")
docker compose exec api python -c "from app.worker import ping; print(ping.delay().get(timeout=10))"

# Celery doesn't auto-reload: restart the workers after changing task code
docker compose restart worker worker-quick

# Reset the local database (wipes all data; used when the schema changes)
docker compose down -v

# Run the tests (uses a separate agoranote_test database; your data is untouched)
docker compose run --rm api pytest
```

The API (`uvicorn --reload`) and the frontend (Vite) reload automatically when you edit code.

## Using a real LLM: local Ollama

By default the AI steps run in **mock mode** (no network, no keys). To generate real study material,
run a model locally with [Ollama](https://ollama.com). The lecture material never leaves your machine
and there are no API costs. Ollama runs **natively on your computer** (not in Docker) so it can use
your GPU; the worker container reaches it at `http://host.docker.internal:11434`.

1. Install Ollama from https://ollama.com/download and start it.
2. Pull the model (~5 GB; fits an 8 GB NVIDIA GPU):
   ```bash
   ollama pull hf.co/unsloth/gemma-4-E4B-it-GGUF:UD-Q4_K_XL
   ```
3. Give Ollama a 16k-token context window (the default 4k is too small) and one request at a time.
   On Windows: quit Ollama from the taskbar, open *Settings → search "environment variables" → Edit
   environment variables for your account*, add these two, then start Ollama again:
   ```
   OLLAMA_CONTEXT_LENGTH=16384
   OLLAMA_NUM_PARALLEL=1
   ```
   (macOS/Linux: see Ollama's FAQ. On Linux, also set `OLLAMA_HOST=0.0.0.0` so containers can reach it.)
4. Check: run a prompt once (`ollama run hf.co/unsloth/gemma-4-E4B-it-GGUF:UD-Q4_K_XL "hello"`), then
   `ollama ps` should show the model with `100% GPU` and `CONTEXT 16384`. If it says 4096, Ollama didn't
   pick up the setting: quit it from the taskbar (and, if your Ollama app has a *Context length* setting,
   set it to 16k), then start it again. With 4096, study sets fail and the worker log says
   "The LLM's context window is too small".
5. In `.env` set:
   ```
   LLM_PROVIDER=openai
   LLM_BASE_URL=http://host.docker.internal:11434/v1
   LLM_MODEL=hf.co/unsloth/gemma-4-E4B-it-GGUF:UD-Q4_K_XL
   LLM_REASONING_EFFORT=none
   ```
   and restart the workers: `docker compose up -d worker worker-quick` (they re-read `.env`).

`LLM_PROVIDER=openai` means "any OpenAI-compatible Chat Completions API", so the same code works with
OpenAI or OpenRouter later: change `LLM_BASE_URL`, `LLM_MODEL` and set `LLM_API_KEY`.

**Speed** (8 GB NVIDIA GPU, ~80 tokens/s): about 2 minutes for a 31-slide lecture and 3-5 minutes for a
71-slide one. Every LLM call is logged with its token counts and speed; follow along with
`docker compose logs -f worker worker-quick`. `LLM_REASONING_EFFORT=none` switches off the model's hidden
"thinking"; with it on (empty value) each call takes ~1.5x longer and, in our tests, the quizzes were
not measurably better.

## Transcribing recordings: local Whisper (speaches)

Uploaded audio/video (`.mp3 .m4a .wav .ogg .webm .mp4`) is converted with ffmpeg to mono 16 kHz MP3,
cut into 10-minute segments and transcribed in order. By default this is mocked too. For real
transcripts, run Whisper locally with [speaches](https://speaches.ai) (faster-whisper behind an
OpenAI-compatible API). It is part of `docker-compose.yml` as an **optional** service under the `gpu`
profile, so a plain `docker compose up` still works on machines without an NVIDIA GPU.

1. Requirements: an NVIDIA GPU and Docker Desktop with GPU support (WSL 2 on Windows). Check with
   `docker run --rm --gpus=all nvidia/cuda:12.6.3-base-ubuntu24.04 nvidia-smi`.
2. Start everything including speaches:
   ```bash
   docker compose --profile gpu up
   ```
3. Download the model once (~1.6 GB, kept in the `hf-hub-cache` volume):
   ```bash
   curl -X POST http://localhost:8001/v1/models/deepdml/faster-whisper-large-v3-turbo-ct2
   ```
4. In `.env` set:
   ```
   TRANSCRIBE_PROVIDER=openai
   TRANSCRIBE_BASE_URL=http://speaches:8000/v1
   TRANSCRIBE_MODEL=deepdml/faster-whisper-large-v3-turbo-ct2
   TRANSCRIBE_VAD_FILTER=true
   SHARED_GPU=true
   COMPOSE_PROFILES=gpu
   ```
   and restart: `docker compose up -d`. `COMPOSE_PROFILES=gpu` makes every plain `docker compose up`
   start speaches too. Without speaches running, recordings fail with "The transcription service
   could not be reached" (text documents still work).

**Sharing one GPU.** Gemma (~5 GB) and Whisper (~2.5 GB) don't fit in 8 GB together. With
`SHARED_GPU=true` every GPU call (one LLM request, or one audio segment) takes a lock in Redis, so they
take turns; before each segment Ollama is told to unload Gemma, and speaches unloads Whisper after each
request (`WHISPER__TTL=0` in docker-compose.yml). Study sets are processed one at a time by the
`worker` service, and replacement quiz questions run on their own `worker-quick` service, so after a
wrong answer the new question comes within about a minute even during an hour-long transcription.

**Language** is detected by Whisper on the first segment and then passed for all other segments.
`TRANSCRIBE_VAD_FILTER=true` skips silence before transcribing (faster, and no invented words in
silence); it is a speaches-only option, so keep it `false` with OpenAI.

For the hosted version, the same code works with OpenAI: `TRANSCRIBE_BASE_URL=https://api.openai.com/v1`,
`TRANSCRIBE_MODEL=whisper-1`, `TRANSCRIBE_API_KEY=...`, `TRANSCRIBE_VAD_FILTER=false`, `SHARED_GPU=false`.

## Signing in: Clerk

With `AUTH_MODE=dev` (the default) there is no login: everyone is the same development user. Real
accounts use [Clerk](https://clerk.com): visitors sign in or create an account in Clerk's own forms,
and each user only sees their own study sets.

1. Create a free account at https://dashboard.clerk.com and create an application; pick the sign-in
   options you want (e.g. email and Google). A new application is a *development instance*, which is
   what local development uses.
2. On the application's **API keys** page, copy the **Publishable key** (`pk_test_…`) and the
   **Frontend API URL** (`https://….clerk.accounts.dev`).
3. In `.env` set:
   ```
   AUTH_MODE=clerk
   AUTH_ISSUER=<the Frontend API URL>
   VITE_AUTH_MODE=clerk
   VITE_CLERK_PUBLISHABLE_KEY=<the publishable key>
   ```
   and restart: `docker compose up -d` (the containers re-read `.env`).
4. Optional, to store users' email addresses: in the Clerk dashboard, customize the session token and
   add the claim `{"email": "{{user.primary_email_address}}"}`. Without it the app works the same,
   the email column just stays empty.

How it works: after signing in, the frontend sends Clerk's short-lived session token with every API
request (`Authorization: Bearer …`). The API checks the token's signature with Clerk's public keys
(downloaded from `AUTH_ISSUER/.well-known/jwks.json`), its expiry, its issuer and the website it was
issued for, and then uses Clerk's user id. No Clerk secret key is needed. Study sets created in dev mode
belong to the development user, so they don't appear after switching to Clerk.

### Deleting accounts

When a Clerk account is deleted (by the user under *Manage account → Security → Delete account*, or by
you on the dashboard's **Users** page), Clerk sends a `user.deleted` webhook to
`/api/webhooks/clerk`, and the API deletes everything it keeps for that user: study sets, chapters,
quiz progress, display settings and the uploaded files and transcripts in storage. The message is
signed by Clerk; the API checks the signature with the endpoint's signing secret and refuses anything
else.

1. Clerk must be able to reach the API, so it needs a public `https` URL. Deployed, that is the API's
   own address. Locally, a temporary [Cloudflare quick tunnel](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/trycloudflare/)
   gives one (no account needed; the URL changes every time it starts):
   ```
   docker run --rm --network agoranote_default cloudflare/cloudflared:2026.11.1 tunnel --no-autoupdate --url http://api:8000
   ```
   It prints an address like `https://some-words.trycloudflare.com`.
2. In the Clerk dashboard open **Webhooks → Add Endpoint**. Endpoint URL: the public address +
   `/api/webhooks/clerk`. Under events, tick only `user.deleted`. Create it.
3. Copy the endpoint's **Signing Secret** (`whsec_…`) into `.env` as `CLERK_WEBHOOK_SIGNING_SECRET`
   and restart the API: `docker compose up -d api`.
4. To test, delete a test account; the endpoint's **Message Attempts** in Clerk should show
   *Succeeded*, and that user's study sets are gone. A new tunnel URL means editing the endpoint URL
   in Clerk (the signing secret stays the same).

## Storing uploads: Cloudflare R2

Locally, uploads are kept in a Docker volume (`STORAGE_BACKEND=local`). For the deployed app they go to
[Cloudflare R2](https://developers.cloudflare.com/r2/), Cloudflare's object storage, because the API and
the workers run on separate machines there and need one shared place for files.

1. In the Cloudflare dashboard open **R2** and create a bucket (e.g. `agoranote-uploads`). Leave public
   access off: the bucket stays private, only the API and the workers use it.
2. Under **R2 → Manage API tokens**, create an API token with **Object Read & Write** permission for that
   bucket. Copy the **Access Key ID** and **Secret Access Key** (the secret is shown only once), and note
   your **Account ID**.
3. In `.env` set:
   ```
   STORAGE_BACKEND=r2
   R2_ACCOUNT_ID=<account id>
   R2_ACCESS_KEY_ID=<access key id>
   R2_SECRET_ACCESS_KEY=<secret access key>
   R2_BUCKET=agoranote-uploads
   ```
   and restart: `docker compose up -d`. The API and workers refuse to start if one of these is missing.

The app talks to R2 with `boto3` (R2 speaks the S3 API) at `https://<account id>.r2.cloudflarestorage.com`.
Each upload is stored as `users/<user>/sets/<set>/<n>-<file name>`, transcripts next to their recording;
deleting a study set deletes its objects. Files uploaded while `STORAGE_BACKEND=local` stay in the local
volume and are not moved to R2, so switch before creating the study sets you want to keep.

## Deployment (Railway)

The deployed app runs on [Railway](https://railway.com) as five services in one project. The AI is
OpenAI (`gpt-6-luna` and `gpt-transcribe`), files go to Cloudflare R2 and sign-in is Clerk:

| Service    | What it is                         | Built from                    | Public address |
|------------|------------------------------------|-------------------------------|----------------|
| `Postgres` | Railway's PostgreSQL               | Railway template              | no             |
| `Redis`    | Railway's Redis (the Celery queue) | Railway template              | no             |
| `api`      | FastAPI                            | `backend/Dockerfile`          | yes            |
| `worker`   | Celery, both queues                | `backend/Dockerfile`          | no             |
| `frontend` | the built React app, via `serve`   | `frontend/Dockerfile`         | yes            |

Everything is set in Railway's dashboard; the repository has no Railway config files (Railway's
`railway.json` "config as code" is being retired). Railway builds from GitHub and redeploys on every push.

### 1. Before you start

- The code on GitHub, in a **private** repository. `.env` and `samples/` are git-ignored and never uploaded.
- An OpenAI API key (project "AgoraNote", with a monthly spend limit), the R2 bucket and token
  (see *Storing uploads*), and the Clerk instance (see *Signing in*).
- A Railway account (sign in with GitHub). The **Hobby** plan ($5 a month, including $5 of usage)
  keeps the app running; a trial account is enough to try it.

### 2. Create the project and the databases

1. Railway dashboard → **New Project → Empty project**.
2. **+ Create → Database → PostgreSQL**, then **+ Create → Database → Redis**. Keep their names
   `Postgres` and `Redis`: the variables below refer to them by name.
3. For each service (these two and the three below): **Settings → Deploy → Regions** →
   **EU West (Amsterdam)**. The privacy page says the data is in the Netherlands.

### 3. Shared variables (the secrets, typed once)

**Project Settings → Shared Variables**, add:

```
OPENAI_API_KEY=sk-...
R2_ACCOUNT_ID=...
R2_ACCESS_KEY_ID=...
R2_SECRET_ACCESS_KEY=...
R2_BUCKET=...
AUTH_ISSUER=https://your-app-12.clerk.accounts.dev
CLERK_WEBHOOK_SIGNING_SECRET=whsec_...
```

### 4. The `api` service

1. **+ Create → GitHub Repo →** your repository. Rename the service `api` (click its name).
2. **Settings → Source → Root Directory**: `/backend`. Railway finds `backend/Dockerfile` and uses it.
3. **Settings → Deploy → Healthcheck Path**: `/api/health`.
4. **Settings → Networking → Generate Domain**. This gives `https://api-….up.railway.app`.
5. **Variables → Raw Editor**, paste:

```
ENV=production
FRONTEND_URL=https://${{frontend.RAILWAY_PUBLIC_DOMAIN}}
DATABASE_URL=${{Postgres.DATABASE_URL}}
REDIS_URL=${{Redis.REDIS_URL}}
AUTH_MODE=clerk
AUTH_ISSUER=${{shared.AUTH_ISSUER}}
CLERK_WEBHOOK_SIGNING_SECRET=${{shared.CLERK_WEBHOOK_SIGNING_SECRET}}
STORAGE_BACKEND=r2
R2_ACCOUNT_ID=${{shared.R2_ACCOUNT_ID}}
R2_ACCESS_KEY_ID=${{shared.R2_ACCESS_KEY_ID}}
R2_SECRET_ACCESS_KEY=${{shared.R2_SECRET_ACCESS_KEY}}
R2_BUCKET=${{shared.R2_BUCKET}}
LLM_PROVIDER=openai
LLM_BASE_URL=https://api.openai.com/v1
LLM_MODEL=gpt-6-luna
LLM_API_KEY=${{shared.OPENAI_API_KEY}}
LLM_REASONING_EFFORT=none
TRANSCRIBE_PROVIDER=openai
TRANSCRIBE_BASE_URL=https://api.openai.com/v1
TRANSCRIBE_MODEL=gpt-transcribe
TRANSCRIBE_API_KEY=${{shared.OPENAI_API_KEY}}
TRANSCRIBE_VAD_FILTER=false
SHARED_GPU=false
MAX_STUDY_SETS_PER_DAY=5
```

The API refuses to start with `AUTH_MODE=dev` when `ENV=production`, or with `r2` missing a setting.
It creates the database tables itself on its first start.

### 5. The `worker` service

1. **+ Create → GitHub Repo →** the same repository. Rename it `worker`.
2. **Root Directory**: `/backend`.
3. **Settings → Deploy → Custom Start Command**:
   `celery -A app.worker worker --loglevel=info -Q processing,quick --concurrency=2`
   (one worker for both queues, two tasks at a time; locally there are two workers because of the GPU).
4. No domain: nothing calls the worker; it takes its tasks from Redis.
5. **Variables → Raw Editor**: the same block as the `api` service.

### 6. The `frontend` service

1. **+ Create → GitHub Repo →** the same repository. Rename it `frontend`.
2. **Root Directory**: `/frontend`. Railway uses `frontend/Dockerfile` (build with Vite, then
   `serve -s dist`, which also answers addresses like `/sets/12` with the app).
3. **Settings → Networking → Generate Domain**.
4. **Variables → Raw Editor**:

```
VITE_API_URL=https://${{api.RAILWAY_PUBLIC_DOMAIN}}
VITE_AUTH_MODE=clerk
VITE_CLERK_PUBLISHABLE_KEY=pk_test_...
```

These are read while the app is **built** (the Dockerfile declares them with `ARG`), so changing one
needs a redeploy of `frontend`, which Railway offers after every variable change.

### 7. Clerk

- The development instance (`pk_test_…`) works on the `….up.railway.app` address. Its sign-in shows a
  "Development mode" label. A Clerk **production** instance needs a domain you own (Clerk asks for DNS
  records), so it can only follow with a custom domain.
- **Webhooks**: edit the `user.deleted` endpoint's URL to `https://<api address>/api/webhooks/clerk`.
  The signing secret stays the same. Test by deleting a test account (see *Deleting accounts*).

### 8. Check it

1. `https://<api address>/api/health` → `{"status":"ok"}`.
2. Open the frontend address, sign in, upload a document and a recording. The `worker` service's
   **Logs** show each step, the tokens used by every LLM call and the seconds of audio transcribed.
3. OpenAI's **Usage** page shows the cost; Railway's **Usage** page shows the hosting cost.

Every push to the repository's main branch redeploys the services. A schema change means emptying
the database: there are no migrations yet.
